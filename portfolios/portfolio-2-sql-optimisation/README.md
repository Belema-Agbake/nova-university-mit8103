# Portfolio 2: SQL optimisation

## Scope

All benchmarks run only against the local, isolated
`nova_university_benchmark` PostgreSQL database. Production Cloud SQL is never
contacted or modified. The benchmark dataset contains 10,000 fictional
students and 40,000 registrations, generated by `seed-large-dataset.ts`.

The exact SQL is in `baseline.sql`. Candidate indexes are in
`optimisations.sql` and are applied only to the benchmark database.

## Repeated 10,000-student benchmark

Each query has one warm-up run followed by eleven measured
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` runs. The generated report includes
all samples, execution plans, median and P95 timing.

| Query | Median | P95 |
| --- | ---: | ---: |
| Student registered courses | 1.353 ms | 1.837 ms |
| Available course offerings | 0.858 ms | 1.532 ms |
| Lecturer assigned courses | 1.101 ms | 1.320 ms |
| Lecturer course roster | 1.184 ms | 1.467 ms |
| Administrator pending approvals | 0.896 ms | 1.360 ms |
| Student published results | 1.665 ms | 2.276 ms |
| Outbox pending-delivery queue | 2.439 ms | 3.726 ms |

All observed P95 values are below four milliseconds in this local,
fictional-data benchmark. These timings demonstrate local query behaviour, not
a production service-level guarantee.

## Index analysis

- `registrations(studentId, status, courseOfferingId)` targets student
  registration retrieval.
- `results(status, submittedAt, id) INCLUDE (registrationId)` targets the
  administrator approval queue's status/order/limit pattern.

The captured baseline and candidate-index plans are retained in
`explain-results/`. Whether the planner selects an index depends on the query
selectivity and table size; sequential scans remain valid for small result
sets.

## Reproduce

```powershell
npm run benchmark:sql:seed
npm run benchmark:sql
```

The JSON and Markdown evidence files are written to `explain-results/`.
